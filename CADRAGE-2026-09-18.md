# Cadrage Annotate — session du 2026-09-18

*Issu de la session de cadrage produit (7 étapes). Complète BRIEF_Annotate.md sans le remplacer — ce fichier documente les décisions prises, BRIEF_Annotate.md reste la vision d'origine.*

## Étape 1 — Inspiration retenue

- **BugPilot** (open source, github.com/rodlunt/bugpilot) : widget → issue GitHub structurée (texte humain + bloc JSON machine) → triage IA → validation humaine → PR. Pattern à s'inspirer pour le format de rapport et le principe de validation avant action, PAS pour l'infra (pas de GitHub Actions/Cloudflare — on a déjà une session IA en direct).
- **Linear + Copilot cloud agent** : confirme le pattern standard "ticket → agent assigné → PR draft à valider".
- **Marker.io** : capture écran + métadonnées techniques avancées + intégrations multiples — inspiration pour la richesse du rapport.
- **Écarté** : répliquer l'infra BugPilot telle quelle (trop lourd vs solo) ; Vercel Toolbar comme mécanisme de déclenchement (pas de webhook fiable pour ça).

## Étape 2 — Fiche rapport (V1, définie)

Chaque ticket contient :
- Commentaire en texte libre
- Catégorie posée automatiquement par **règles/mots-clés locales, zéro IA** (bug visuel / bug fonctionnel / ajustement visuel [taille, largeur, dropdown...] / texte à changer / changement de comportement / suggestion / question)
- Bloc technique structuré capturé automatiquement (sélecteur DOM, chemin de page, position fractionnelle, résolution, navigateur, capture d'écran de la zone, erreurs console récentes) — affiché en priorité selon la catégorie, pas systématiquement tout montré
- Statut simple (nouveau / traité), modifiable à la main
- Projet, page, date

Consultation V1 : vue liste existante (groupée par page) + export du rapport entier (texte + JSON) + marquage/suppression d'un ticket individuellement.

**Point de vigilance conservé** : catégorisation IA plus fine possible, mais seulement en différé, de son côté (jamais en direct sur le poste de l'utilisateur final) — ligne rouge : pas d'IA qui scanne les données au moment de la saisie.

## Étape 3 — Parcours utilisateur final (V2)

1. Raccourci secret → bouton/pastille apparaît (invisible par défaut sur site prod)
2. Clic sur élément précis OU dessin d'une zone libre (capture libre — retenue, un peu plus de dev que le clic seul)
3. Rédaction du commentaire, reformulation simple proposée à la demande (bouton volontaire, jamais automatique)
4. Confirmation + accès à une liste de ses propres retours avec statut (nouveau/en cours/résolu) — **V2 uniquement**, impossible en V1 (pas de backend partagé)

## Étape 4 — Architecture V1/V2

- **Identification projet** : attribut `data-project="nom"` sur la balise `<script>`, choisi à la main une fois par François à l'installation (pas de saisie à l'exécution). `data-mode="mock"` ou `"live"` bascule le comportement.
- **Schéma Supabase minimal** : `id`, `projet`, `page`, `texte`, `categorie`, `statut`, `donnees_techniques` (JSON), `date_creation`, `auteur` (optionnel, anonyme).
- **Sécurité V2 (version simple retenue pour démarrer)** : clé anonyme Supabase + policy d'écriture "ajout seul" (jamais lecture/modif/suppression des autres commentaires) + limite de fréquence simple côté navigateur.
  - **⚠️ À reposer explicitement à CHAQUE nouveau déploiement sur un projet** : est-ce que ce niveau simple suffit encore, ou faut-il muscler (captcha/Turnstile, validation serveur, rate-limit renforcé côté Cloudflare, alerte sur pic anormal) ? Ne jamais reconduire par défaut sans se reposer la question — risque de croire l'outil "sûr" alors qu'il ne l'est plus pour un contexte à trafic public plus large.
- **Hébergement du script** : **GitHub public + jsDelivr**, tranché. Versioning fiable par tag, gratuit, indépendant de Supabase.

## Étape 5 — Pipeline vers une session IA

- **Déclenchement** : hybride dans le temps — manuel au début (François lance lui-même la session à partir d'un export, pour suivre et prendre confiance), automatique plus tard, mais **jamais sans compte-rendu visible** de ce qui a été fait.
- **Échelle d'autonomie** :
  - Niveau 0 — rapport noté, aucune action
  - Niveau 1 — diagnostic/proposition à relire, pas de code touché
  - Niveau 2 — correctif sur une branche séparée, à valider avant intégration
  - Niveau 3 — application directe, uniquement pour des corrections mineures pré-définies (ex : faute de texte)
- **Granularité du réglage** : **la catégorie du rapport est le réglage principal** (chaque type a un niveau par défaut) ; possibilité d'ajouter un override par projet plus tard si un besoin réel apparaît (pas configuré dès le départ).
- **Format de sortie** : distinction retenue —
  - **Mode maquette (V1, pas de repo)** : fichier structuré (texte + bloc JSON) donné directement à une session
  - **Mode live (V2, projet avec repo de code)** : **issue GitHub** créée automatiquement par rapport (texte + bloc JSON dedans), avec statut ouvert/résolu natif et historique centralisé — se branche naturellement sur le mécanisme "assigner à un agent" (comme Linear/Copilot vu à l'étape 1)

## Étape 6 — Module RAG d'accompagnement (V3, non prioritaire)

- Portée : **module optionnel du même script**, pas un chantier séparé — activable projet par projet
- Base de connaissance : FAQ/doc du produit sur lequel le widget est posé
- Déclenchement : **bouton volontaire uniquement** ("Aide-moi à formuler mon retour") — jamais de détection automatique d'un utilisateur "bloqué" (ce serait une forme de surveillance passive)
- IA locale annoncée à l'utilisateur (transparence sur le fait que ses données ne quittent pas le site) — compatible avec la ligne rouge de confidentialité
- Un vrai RAG complet et plus poussé reste une idée pour plus tard, à construire projet par projet si le besoin se confirme (pas engagé)

### Ce qu'on ne fait pas dans ce chantier, et pourquoi (trade-off assumé)
- Pas de déclenchement automatique de toute action IA sans geste volontaire de l'utilisateur → moins fluide, mais respecte la ligne rouge confidentialité (non négociable).
- Pas de sécurité renforcée (captcha, validation serveur) dès le départ → risque de spam accepté tant que le trafic reste faible ; **à réévaluer à chaque nouveau déploiement**.
- Pas de réglage d'autonomie par projet comme mécanisme principal → moins de contrôle fin par client au début, plus simple à raisonner ; ajoutable plus tard sans tout refaire.
- Pas de vrai RAG complet maintenant → moins d'accompagnement immédiat pour l'utilisateur final, mais évite d'ouvrir un chantier séparé qui retarderait V1/V2.

### Ce qui reste à trancher par François seul
- Nom définitif du produit ("Annotate" = nom de code)
- Modèle IA local à utiliser pour le futur module RAG (non exploré)
- Moment exact du passage déclenchement manuel → automatique sur le pipeline V2
- Mapping précis catégorie → niveau d'autonomie par défaut (l'échelle existe, pas encore le tableau complet) — probablement à faire après un premier usage réel

### Première action concrète (résultat visible rapidement)
Fusionner les 3 fichiers sources actuels (CSS + HTML + JS) en un seul script `.js` autonome qui s'injecte lui-même. Aucune nouvelle décision produit nécessaire — juste du repackaging du code déjà validé. Résultat testable en quelques minutes : coller une seule ligne sur une page test au lieu de 3 blocs à copier-coller. C'est la victoire rapide qui prouve que le repackaging marche, avant d'ajouter capture libre, export ou catégorisation.

## Complément du 2026-09-20 — Extension de navigateur (V2.5, décidée)

**Décision** : `annotate.js` reste le cœur unique du produit. Une **extension de navigateur "enveloppe"** sera ajoutée après le mode partagé (V2) : elle se contente d'injecter ce même script dans l'onglet courant et d'offrir le panneau latéral natif du navigateur. Deux façons de déclencher le même outil, même stockage :
- **balise `<script>`** posée par François sur le site → pour les clients (rien à installer de leur côté) ;
- **extension** → pour François, sur n'importe quel site sans rien y installer (SaaS en prod, site tiers, maquette reçue).

**Pourquoi pas l'extension seule** : demander à des clients d'installer une extension (Chrome d'abord, Safari/Firefox à refaire séparément) est un frein ; la balise reste le canal client.

**Ce qu'apporte l'extension** : annoter sans toucher au site ; vrai panneau latéral (la page se réorganise réellement, sans l'astuce "marge + éléments fixes" codée le 20/09) ; aucune trace dans le code du site.

**Compatibilité** : tout navigateur Chromium (Chrome, Brave, Edge, Arc, Opera, Vivaldi) via le Chrome Web Store. Safari et Firefox : versions séparées, non prévues.

**Distribution restreinte possible** (Chrome Web Store) : *non répertoriée* (lien seulement), *testeurs de confiance* (liste de comptes Google, ≤ 100), *privée* (domaine Google Workspace). Pour le développement et l'usage perso : chargement "non empaquetée" en mode développeur, sans store.

**Sécurité — à respecter le moment venu** :
1. Permissions minimales : `activeTab` uniquement (agit seulement sur l'onglet où l'on clique le bouton), pas de `host_permissions` larges.
2. Manifest V3 interdit le code distant : `annotate.js` doit être **embarqué** dans l'extension (pas chargé depuis jsDelivr) → chaque nouvelle version du script implique une nouvelle version de l'extension à publier (revue Google : quelques jours).
3. Données : mode maquette = rien ne quitte le navigateur ; mode partagé = uniquement vers le Supabase du projet. À écrire tel quel dans la politique de confidentialité exigée par le store. Compte développeur : 5 $ une fois.

**Coût estimé de l'enveloppe** : une session, une fois le cœur stabilisé. Tout le travail V1/V2 lui sert tel quel.

## Complément du 2026-09-21 — Cycle de vie d'un ticket et retour (V1, livré)

Décidé avec François le 20/09 en construisant l'étape 4 (remplace le « statut simple nouveau / traité » de l'étape 2) :
- Statuts : **nouveau → signalé (date) → pris en compte → résolu**, avec une branche **complément demandé** (question de la session) à laquelle l'utilisateur répond sans modifier son texte d'origine. Le ✓ manuel = « résolu par moi ».
- **Verrouillage** : tout ce qui a quitté « nouveau » n'est plus modifiable. Un « signalé » pas encore pris en compte peut être **rouvert** (redevient nouveau, renvoyé au prochain rapport avec « remplace la version du … ») — c'est l'« annule et remplace », au ticket près.
- **Rapport** : fichier `.md` unique (texte + JSON par ticket + consigne de réponse), identifiant `R-AAAA-MM-JJ-n` mémorisé par les tickets ; périmètre par défaut **nouveautés**, option « complet ». Générer = marquer signalés (après confirmation).
- **Retour** en V1 : bloc texte normé collé dans le tiroir (une ligne par ticket : id, statut, message). En V2 (Supabase / issues GitHub) le même format arrivera automatiquement — rien à refaire côté widget.
